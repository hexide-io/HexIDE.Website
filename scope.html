Scope

Where HexIDE stops.

Most projects publish what they can do. This page is the other half, because a limit you find on day three is a bug report, and a limit you read about on day one is a decision you can make.

It is updated with every release. This version describes 0.3.0.

The workbench

Designer, toolbox, menu editorWorksThirteen controls in the toolbox, at VB6's own sizes and names. Line and the ProgressBar load from a form but aren't in the toolbox yet.
Controls HexIDE doesn't modelPartialAn ImageList, a Toolbar or any third-party control shows as a labelled box where VB6 draws it, and saves unchanged. F5 refuses the form.
UserControls and PropertyPagesPartialThey open in their designers and save as VB6 writes them. They don't run.
Object Browser and FindPartialThe Object Browser is incomplete, and Find has no project scope.
MDI forms, printing, Procedure AttributesNot yetEach is tracked as an issue.
Autosave and crash recoveryNot yetSave often, and work on a copy.

Files and saving

VB6's template formsWorksAll 22 designer files VB6 itself ships survive a save byte for byte.
Project filesWorks.vbp files round-trip with their line order and description kept.
EncodingsWorksSources are read in your ANSI code page and keep their encoding. An edit the code page can't hold is refused before anything is written.
Your own projectsPartialAnything HexIDE doesn't understand is preserved, not dropped. Preserved isn't the same as tested. See what a save changes.
Project groupsPartialGroups open and save. Make Project Group isn't built yet.

Running your program

Forms and eventsWorksSeveral forms with Load, Show, vbModal and Unload. Mouse, double-click, focus and Activate events fire.
Files and settingsWorksText, Random and Binary files, the filesystem statements, and GetSetting.
The languagePartialOf 1,184 names, 577 run in full and 435 in part. 143 stop the program with a message naming what's missing. The full list.
Wrong answersPartialSeven names can give a wrong answer without an error. Each one is listed there, with its issue.
Control propertiesPartialA TextBox ignores MaxLength, Locked, PasswordChar and Alignment; a ComboBox has no Sorted. The CommonDialog has Open, Save As and Font, not Color, Printer or Help.
Windows API and COMNot yetA module with Declare loads, but the call fails. CreateObject and type libraries don't work.
GoSub, On…GoTo, ParamArrayNot yetThese need a different way of walking the program, and are tracked.
Screen, Printer, graphicsNot yetThe Screen and Printer objects, the graphics methods, LoadPicture, SendKeys and Shell.

Debugging and making

The debuggerWorksBreakpoints, stepping, Locals, Watches, the Call Stack and an Immediate window that evaluates. Debug on an unhandled error breaks on the statement.
Outside debug adaptersWorksRun, Start External Debug Session drives a debug adapter you supply.
Make EXEPartialBuilds a program that needs neither HexIDE nor .NET. A made program stops silently on a run-time error, and made programs on macOS are untested.
Making with VB6WorksOn Windows with VB6 installed, HexIDE drives the real compiler.

What the editor knows

Syntax and structureWorksSyntax errors as you type, the two VB6 combos, quick info, folding, formatting, and keyword and declared-name completion. Signature help covers VB6's built-in functions.
Rename, go to definitionPartialWithin one file, and by matching text rather than meaning.
Outside language serversWorksAttach any LSP server in lsp-servers.json, and read what crossed the wire in the Protocol Inspector.
Whole-project understandingBy designCross-file references, type-aware completion after a dot, semantic diagnostics: the job of a language engine, attached through that seam.

Saving

What a save changes.

Writing a project back is the half that can lose your work, so it is measured rather than estimated: against the 22 designer files in VB6's own Template folder. Microsoft wrote those, so any difference between what goes in and what comes out is a defect.

All 22 now survive a save byte for byte. What follows is what's left.

A form HexIDE can't reproduce won't save
If a form carries something HexIDE can't write back, it opens read-only and Save declines, rather than putting a lossy copy over your original.
Twenty-two files isn't every file
A real project of any age carries controls and header lines those templates never had. HexIDE preserves what it doesn't understand, but preserved isn't tested. That is the honest reason to keep a backup.
Where the measure runs
Against VB6's template folder wherever VB6 is installed, and against the demos on every build. It can only be lowered by fixing something.
Refusing beats guessing
A refusal is recoverable. A silently rewritten project that only fails the next time VB6 opens it is not.

Permanent

By design, and not changing.

These are deliberate, and they are why the rest of the project stays small enough to finish.

The interpreter is not a compiler
It exists so you can press F5 and watch your program run, and it runs typical form programs. It is not a migration path. Where it differs from VB6, the difference is written down.
No native compiler
HexIDE doesn't emit machine code. On Windows with VB6 installed it drives the real compiler: a bridge to the genuine article, not a copy of it.
No whole-program analysis
The built-in language tooling works on syntax. Binding names across files, inferring types and refactoring need a compiler front end, and that belongs to a real language engine behind a replaceable seam.
Classic dialects only
The interpreter runs the language as Microsoft shipped it. When it meets something it doesn't recognise, it fails clearly rather than guessing.
Some of VB6 isn't coming back
SDI mode, User Documents, DHTML and IIS applications, the Data Environment, the Package and Deployment Wizard, SourceSafe, and COM add-in hosting.

Why publish this

A map is more useful than a promise.

The interpreter's behaviour is checked against the real compiler, VB6 with Service Pack 6, rather than against anybody's memory of it, and that has overturned the obvious answer many times. It produces two things: a runtime that behaves correctly where it works, and an exact record of where it doesn't.

Publishing the second one costs nothing, and saves you an afternoon.
